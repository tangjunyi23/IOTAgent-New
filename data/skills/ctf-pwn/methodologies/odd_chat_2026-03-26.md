# CTF Pwn Methodology: odd_chat

**Date**: 2026-03-26
**Binary**: `attachment`
**Architecture**: `x86_64`
**Mitigations**: `NX`, `Partial RELRO`, `No PIE`, `Canary`, `No seccomp observed`
**Vulnerability Class**: signed-length bypass to heap overflow plus tcache poisoning
**Primitives**: arbitrary-length heap write via `INT_MIN`, libc leak via forged list node, tcache `fd` poisoning, GOT overwrite to `system`
**Reuse Tags**: heap-overflow, tcache
**User-Provided ida-no-mcp Pseudocode**: no

## 1. Snapshot

- Goal: exploit `39.106.48.123:32818` and recover the remote flag.
- Artifacts used: local `attachment`, bundled `libc.so.6`, and the recovered Ubuntu glibc bundle `2.27-3ubuntu1.6_amd64`.
- Runtime quirk: headless IDA export could not run because the local IDA install had no valid license, so the solve stayed evidence-driven from disassembly and live trials.

## 2. Ground Truth

- `attachment` is a non-PIE amd64 ELF with `NX`, `Partial RELRO`, and a stack canary. The binary keeps a singly linked chat-history list of `malloc(0x20)` chunks where the first `0x18` bytes are chat text and `+0x18` is the `next` pointer.
- The apparent input clamp is deceptive. The chat path reads an integer, applies a branchless absolute value, then reduces it modulo `24`. For normal values this keeps the write within `0x18` bytes, but `INT_MIN` survives the branchless `abs` as `-0x80000000`, and the later modulo math leaves the final length as `-8`.
- The character reader compares `count < len` with `jb` rather than a signed comparison. When `len == -8`, that becomes `count < 0xfffffff8`, so input continues until newline and returns the true byte count. That turns the menu into an arbitrary-length heap write.
- After each read, the program TEA-encrypts 8-byte blocks in place. Exploitation therefore needs preimages: send `TEA^{-1}(desired_qword)` so the stored bytes become the chosen pointer or metadata after encryption.
- The history printer walks `next` pointers and prints each node with `%s`. Overwriting the head chunk’s `next` with the executable’s copied `stdout` pointer at `0x6020a0` makes the second “history” node print the libc `stdout` pointer bytes, yielding `libc_base` after subtracting `_IO_2_1_stdout_`.

## 3. Exploit Chain

- Leak stage:
  - Send one oversized chat with `count = INT_MIN`.
  - Write 24 filler bytes plus `TEA^{-1}(p64(0x6020a0))` at offset `0x18`.
  - Use `View chat history` and parse the fake second node to recover the copied `stdout` pointer and compute `libc_base`.
- Heap grooming:
  - The leak chunk is now poisoned with `next = stdout`, so it must not be freed.
  - Allocate a fresh middle chunk and overwrite its `next` field back to `NULL`.
  - Allocate one more chunk on top of it so `Clear chat` frees only this clean two-chunk sublist into the `0x30` tcache bin.
- Tcache poisoning:
  - Reallocate the lower freed chunk and use the same arbitrary-length write to reach the adjacent freed chunk.
  - Preserve the freed chunk header with `size = 0x31`, then overwrite its tcache `fd` with `atoi@got`.
  - The next two `malloc(0x20)` calls return the real freed chunk and then `atoi@got`.
- Code execution:
  - On the forged `atoi@got` allocation, send `TEA^{-1}(p64(system))` as an 8-byte payload so the encrypted write stores the real `system` address into the GOT.
  - Return to the menu and enter `cat /flag`. The program still calls `atoi(choice_buf)`, but the GOT entry now points to `system`, so the menu input becomes a shell command.
- Decisive insight: the apparent “mod 24” bound is fake because `INT_MIN` turns the branchless `abs` into `-8`, and the later unsigned loop comparison upgrades that edge case into a newline-terminated arbitrary heap write.

## 4. Dead Ends Worth Remembering

- Treating the chat length as a hard `0x18` cap was the first trap. The disassembly only makes sense once the `INT_MIN` overflow path is modeled exactly in 32-bit signed arithmetic.
- Clearing the leaked history chunk immediately after the `stdout` leak crashes: its forged `next` points at `.bss`, so `clear chat` eventually reaches `free(0x6020a0)`. The earlier signal was that the leak primitive reuses the live list pointer, not a throwaway buffer.
- A direct `__free_hook` route would have worked too, but partial RELRO plus a fixed `atoi@got` made the final stage shorter and avoided having to keep a `/bin/sh` chunk alive until `free`.

## 5. Lessons to Reuse

- Signals to watch for:
  - branchless `abs` or hand-rolled sign normalization in front of a size calculation
  - later unsigned compares (`jb`, `ja`, `jbe`, `jae`) against that supposedly sanitized length
  - in-place block ciphers that look like they “destroy” attacker control but are actually reversible with chosen preimages
- Mitigation mix:
  - `No PIE` makes copy-relocation leaks and GOT targets fixed.
  - `Partial RELRO` makes a GOT-overwrite finish simpler than hook-based heap cleanup.
  - Bundled glibc `2.27` means classic tcache poisoning still works without safe-linking.
- Reusable trick:
  - if a leak stage poisons a linked-list `next` pointer, do not free that list node later. Build a separate clean freelist segment for heap grooming instead of trying to recycle the corrupted node.
- Should `patterns.md` be updated: yes. Add a generic warning that branchless `abs` on `INT_MIN`, followed by unsigned length checks, can resurrect a supposedly clamped size into an oversized write primitive.
