# CTF Pwn Methodology: httpd

**Date**: 2026-03-28
**Binary**: httpd
**Architecture**: x86_64
**Mitigations**: Partial RELRO, No PIE, Canary, NX, SHSTK, IBT
**Vulnerability Class**: auth bypass plus stack overflow plus mid-function stack-frame reuse
**Primitives**: empty-token auth bypass, bytewise canary brute, bytewise saved-`rbp` brute, caller-frame local overwrite, libc leak via existing response helper, ret2libc `system(token)`
**Reuse Tags**: stack-overflow, canary-bypass, ret2libc, rop, auth-bypass
**User-Provided ida-no-mcp Pseudocode**: no

## 1. Snapshot

- Goal: exploit the router-like HTTP daemon and recover the flag over the network socket.
- Local artifacts used: the provided ELF plus the bundled `flag` file; no custom libc or loader shipped with the challenge.
- The full exploit chain was validated locally against the provided binary and returned `polarisctf{test_flag}` from the bundled flag file.
- The advertised remote endpoint `nc1.ctfplus.cn:29737` returned `Connection refused` when tested on 2026-03-28, so the remote run could not be validated live from this environment.

## 2. Ground Truth

- `checksec` showed Partial RELRO, No PIE, Canary, NX, and SHSTK/IBT notes.
- The server is fork-per-connection. The parent keeps the same process-wide canary and stack layout across children, which makes bytewise crash-or-success brute force practical.
- Startup leaves the shared `token` string empty. Because `/config` and `/resetPasswd` only compare the incoming cookie against that shared token, `Cookie: token=` is enough to pass auth before any real login.
- `/config` copies attacker-controlled decoded values into fixed stack slots:
  - `route_name` -> `[rbp-0xa0]`
  - `ip` -> `[rbp-0x80]`
  - `subnet_mask` -> `[rbp-0x60]`
  - `gateway` -> `[rbp-0x40]`
- The `gateway` copy is the cleanest final smash because the saved canary is only `0x28` bytes away from the start of that destination.
- The caller frame of `4035a0` is the POST router at `40273e`. Returning into `402ac5` reuses the caller's existing `402c9e` response path, which reads:
  - `fd` from `[caller_rbp-0x154]`
  - `body_ptr` from `[caller_rbp-0x140]`
- By restoring the real caller `rbp` and overwriting those caller locals in-place, the exploit turns the binary's own JSON response helper into a 6-byte arbitrary leak.

## 3. Exploit Chain

- Stage 1: brute the callee canary byte-by-byte through `/config`.
  - Payload stops immediately after the tested canary byte, so the unknown suffix stays untouched.
  - Correct prefix returns `HTTP/1.1 200 OK`; wrong prefix hits the signal handler and returns `500 Internal Server Error`.
- Stage 2: brute the saved caller `rbp` the same way.
  - The overwrite again stops immediately after the tested `rbp` byte, so the untouched suffix keeps the real stack pointer valid.
  - This is the decisive trick: the stack pointer is treated like another prefix-brutable secret.
- Stage 3: leak `read@got` and the shared-mapping pointer.
  - Restore the real caller `rbp`.
  - Overwrite the callee return address with `0x402ac5`.
  - Overwrite `[caller_rbp-0x154] = 4` and `[caller_rbp-0x140] = target_slot`.
  - Leak `read@got` first for a stable libc base.
  - Leak `0x4061f1` rather than `0x4061f0` because the shared mapping is page-aligned and the low byte is always `0x00`.
- Stage 4: use `/resetPasswd` to overwrite the shared token at `shared+0x40` with `cat flag >&4`.
  - The `%00` decoder bug lets `strcmp(new, confirm)` succeed on the prefix `A\x00` while the full decoded write keeps running.
  - `0x20` bytes after the password slot lands exactly on the token.
- Stage 5: final `/config` smash.
  - ROP only needs `ret ; pop rdi ; ret ; system`.
  - Argument is `shared+0x40`, which now contains the shell command string.
  - The command redirects its own stdout to fd `4`, so the exploit does not need `dup2` or any `rdx` gadget.
- Decisive insight: once the service forks and keeps both the canary and caller stack frame stable, you can brute saved `rbp` just like the canary, then re-enter the caller at `402ac5` to transform its own response helper into the libc/shared-pointer leak needed for the final ret2libc.

## 4. Dead Ends Worth Remembering

- The original `/resetPasswd` overwrite is not long enough to reach the nearby `link_map` target directly. Even with the POST `Content-Length` stack overread, decoding stops as soon as the copied request body hits the first real `0x00`, so the huge `link_map` overwrite route is shorter on paper than in reality.
- `/logout` contains a write-length bug in the redirect helper, but the immediate caller truncates the cookie to `0x100`, so that path tops out below the helper's `0x200` stack buffer and does not leak by itself.
- A direct final `dup2(4,0/1/2) + system("/bin/sh")` chain was less reliable than simply storing `cat flag >&4` in the shared token and calling `system(token)`.

## 5. Lessons to Reuse

- In fork-per-connection services, a partial overwrite that stops inside saved `rbp` can turn the frame pointer into another bytewise-brutable secret, not just the canary.
- If a callee returns into a large caller frame, inspect mid-function caller blocks before over-investing in gadget hunts; re-entering a caller-side helper with repaired `rbp` and overwritten caller locals can be a cleaner leak primitive than building `write(fd, addr, len)` from scratch.
- When a command string can include shell redirection to the active socket fd, a final `system(cmd)` may be shorter and more stable than `dup2` or `orw`.
- Should `patterns.md` be updated: yes. Two reusable ideas generalized well here:
  - bytewise brute of saved `rbp` with a fork-server oracle
  - caller-frame reuse as a leak primitive by returning into an existing mid-function helper
