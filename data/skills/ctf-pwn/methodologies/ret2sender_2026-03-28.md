# CTF Pwn Methodology: ret2sender

**Date**: 2026-03-28
**Binary**: chall
**Architecture**: x86_64
**Mitigations**: Partial RELRO, No PIE, No Canary, Executable Stack, SHSTK, IBT
**Vulnerability Class**: stack overflow
**Primitives**: saved return-address overwrite, controlled function argument via ROP
**Reuse Tags**: stack-overflow, rop
**User-Provided ida-no-mcp Pseudocode**: no

## 1. Snapshot

- Challenge goal was a remote shell on `143.198.163.4:15858`, then recover the flag from the spawned `/bin/sh`.
- Local artifacts used: only the provided ELF `chall`; it links against the system loader and libc.
- Remote runtime matched local offsets because the binary is non-PIE and the exploit only needs text addresses.

## 2. Ground Truth

- `checksec` showed Partial RELRO, No PIE, No Canary, executable stack, plus SHSTK and IBT notes in the ELF metadata.
- `objdump -d -Mintel` on `deliver` proved the bug: `gets` writes into `[rbp-0x20]`, so the saved RIP is 40 bytes from the buffer start.
- `objdump` also proved the intended target: `drive` compares its `rdi` argument against `0x48435344`, prints success, and then calls `system("/bin/sh")`.
- Gadget search found `ret` at `0x40101a` and `pop rdi; ret` at `0x4011be`, so no libc leak or stack pivot was required.
- Headless IDA export failed (`idat_exit_code=1`), but disassembly already gave decisive control-flow evidence.

## 3. Exploit Chain

- Send any long line to `deliver`; the menu comparisons are irrelevant once `gets` overflows the 32-byte stack buffer.
- Overflow layout: `0x28` bytes padding, one plain `ret` for stack alignment, `pop rdi; ret`, secret value `0x48435344`, then `drive`.
- The alignment `ret` mattered because returning directly into `pop rdi; ret` would enter `drive` with the stack misaligned by 8 bytes before its libc calls.
- Final route: short non-PIE ROP into the built-in win function, then reuse the spawned shell to run `cat flag*`.
- Decisive insight: the executable stack and menu strings are decoys; once disassembly shows a direct `drive(secret)` win path and an in-binary `pop rdi; ret`, the shortest route is a 40-byte ret2win-style ROP chain.

## 4. Dead Ends Worth Remembering

- Executable-stack shellcode was unnecessary. There was no stack leak, while a fully static text-only ROP chain already solved the challenge with fewer assumptions.
- Headless pseudocode export failed. That was not a blocker because the decisive evidence lived in three small functions (`deliver`, `drive`, `tool`) that were faster to verify with `objdump`.

## 5. Lessons to Reuse

- When strings and function names advertise multiple routes, inspect the win-function signature before spending time on shellcode or libc leaks.
- For non-PIE stack overflows, always check whether the binary already contains both the win function and the argument-loading gadget needed to call it directly.
- CET notes in `checksec` are not enough to rule out classic ROP; validate the actual runtime path before abandoning the easy chain.
- Should `patterns.md` be updated: no. This is a clean instance of an existing `stack-overflow` plus `rop` pattern rather than a new generalized trick.
