# CTF Pwn Methodology: speedpwn

**Date**: 2026-03-21
**Binary**: `chall`
**Architecture**: `x86_64`
**Mitigations**: `NX`, `Partial RELRO`, `No PIE`, `Canary`, `SHSTK`, `IBT`, `No seccomp observed`
**Vulnerability Class**: forward OOB bit write plus uninitialized-value oracle
**Primitives**: forward bit-level arbitrary write in `.bss`, comparator-based libc leak, fake `_IO_FILE` stdin-backed bulk write, GOT overwrite to `system`
**Reuse Tags**: fsop, pie-leak
**User-Provided ida-no-mcp Pseudocode**: no

## 1. Snapshot

- Goal: exploit `challenge.imxbt.cn:32302` and recover the remote flag.
- Artifacts used: local `chall`, bundled `ld-2.39.so`, bundled `libc-2.39.so`, and an existing headless IDA export.
- Remote runtime matched the bundled libc route. The final working exploit used a libc leak first, then a fake `_IO_FILE` with `_IO_file_jumps`, not the earlier `_IO_wfile_jumps` shell pivot.

## 2. Ground Truth

- `chall` is a non-PIE amd64 ELF with `NX`, `Partial RELRO`, stack canary, `SHSTK`, and `IBT`.
- `fight_bot()` updates `*((u64*)&game_history + number_of_games / 64)` with a single-bit set or clear and then increments `number_of_games`. This is a deterministic forward bit write starting at `0x404088`.
- `print_game_history()` is not a general read. Disassembly shows it always reads the qword at `number_of_games / 64`, masks with `1 << (i % 64)`, and compares the result to literal `1`, so it only meaningfully leaks bit 0 under very narrow conditions.
- The decisive leak comes from `simulate()`, not from `print_game_history()`. Sending `-` to `scanf("%llu%*c", &bot_num)` leaves a previously loaded libc return-site value in the argument register path, and the custom `cmp()` comparator exposes that unknown value through win or lose answers.
- The leaked value is a return address at `libc_base + (_IO_default_uflow + 0x32)`. On this glibc 2.39 build, the oracle reconstruction always produced `real_leak + 0x400000000000`, so the usable normalization was:
  - `leaked_addr = reconstructed - 0x400000000000`
  - `libc_base = leaked_addr - 0x955c2`

## 3. Exploit Chain

- Leak stage:
  - Query `simulate()` with crafted player values against the custom `cmp()` comparator.
  - First recover the popcount of the hidden libc address by testing `(1 << e) - 1`.
  - Then recover the set-bit positions one by one by comparing adjacent masks with equal popcount, exactly as in the public solve algorithm.
  - Normalize the reconstructed value by subtracting `0x400000000000`, then subtract `0x955c2` to recover `libc_base`.
- Write stage:
  - Use the forward bit write to place a fake `FILE` at `0x4040a0` and point `seed_generator` at it.
  - The fake object uses `_IO_file_jumps`, `_fileno = 0`, `_IO_buf_base = fread@got`, and `_IO_buf_end = game_history + 8`.
  - On `reseed()`, `fread(&seed, 1, 8, fake_fp)` forces a `read(0, fread@got, payload_len)` from stdin into the GOT and nearby globals.
- Trigger stage:
  - Feed a second-stage stdin payload beginning with `p64(game_history)`, so the in-progress `fread` copies `0x404088` into `seed`.
  - Overwrite `srand@got` with `system`, restore the other adjacent GOT or copy-relocation slots that get clobbered by the contiguous write, and write `/bin/sh\x00` into `game_history`.
  - When `reseed()` continues, the next call is `srand(seed)`, but the GOT now routes it to `system(0x404088)`, which becomes `system("/bin/sh")`.
- Decisive insight: the intended leak is the comparator oracle in `simulate()`, and the shortest post-leak route is a fake `_IO_file_jumps` object that turns the next `fread` into a stdin-backed bulk write over the GOT, so the following `srand` call becomes `system(game_history)`.

## 4. Dead Ends Worth Remembering

- Treating `print_game_history()` as an arbitrary read was a trap. The compare-to-`1` disassembly should have killed that idea immediately.
- The first local shell used `_IO_wfile_jumps` and a forged wide vtable to call `system`, but remote solving stalled because that route still needed libc base first.
- Trying to shift the real `/dev/urandom` `FILE*` around its heap object did not produce a useful no-base leak. Runtime scans showed only the original object and the `+0xf8` wide-jump variant reached valid vtables, and the latter crashed before a usable read.
- Searching for a no-base vtable source in the executable’s GOT, `stdin`, and `stdout` copy-relocations was also a dead end. For reachable `number_of_games` values, no unaligned 8-byte window before `0x404088` could synthesize a pointer inside `__libc_IO_vtables`.

## 5. Lessons to Reuse

- Signals to watch for:
  - a menu action that feeds an uninitialized or partially initialized value into a custom comparator
  - a comparator that first checks popcount or another coarse metric before bit order, because that can turn win or lose answers into a full reconstruction oracle
  - a later `fread(..., attacker_controlled_FILE*)` call, because a fake `_IO_file_jumps` object can convert it into a chosen `read(0, target, len)` without needing a wide-vtable call
- Mitigation mix:
  - `No PIE` kept all writable targets and GOT slots stable.
  - `Canary`, `SHSTK`, and `IBT` made direct control-flow hijack unattractive, so the leak plus FSOP route was the right default.
- Reusable trick:
  - use the comparator as an oracle first, then prefer a stdin-backed fake `_IO_FILE` that rewrites the next GOT call already on the current code path.
- Should `patterns.md` be updated: yes. Add the `_IO_file_jumps` stdin-sysread FSOP variant under `fsop`, because it changes route selection when a later `fread` consumes an attacker-controlled `FILE*`.
