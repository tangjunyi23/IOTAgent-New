# CTF Pwn Methodology: music_box

**Date**: 2026-03-29
**Binary**: main
**Architecture**: x86_64
**Mitigations**: NX, PIE, Partial RELRO, Canary, SHSTK, IBT
**Vulnerability Class**: TOCTOU stale-offset race against a compacting custom allocator
**Primitives**: stale offset read, stale offset write, note-header forgery, slot-metadata arbitrary read/write, PIE leak, libc leak, GOT overwrite to `system`
**Reuse Tags**: heap-overflow, pie-leak, ret2libc
**User-Provided ida-no-mcp Pseudocode**: no

## 1. Snapshot

- The service runs two background threads: `MusicBox` keeps allocating and freeing lyric buffers, and `GarbageClean` periodically compacts the live note set into the alternate backing buffer.
- Local artifacts used: `main`, provided `libc.so.6` (`Ubuntu GLIBC 2.35-0ubuntu3.13`), remote endpoint `nc1.ctfplus.cn:40417`.
- No loader was shipped; local validation used the host loader and host libc for end-to-end verification, while the remote exploit used the provided libc for symbol math.

## 2. Ground Truth

- `checksec` showed `PIE`, `NX`, `Canary`, `Partial RELRO`, `SHSTK`, and `IBT`.
- `GetSlotOffset()` reads the current slot offset without taking `g_mutex`, but `EditNote()` / `ShowNote()` take `g_mutex` later and interpret that stale offset against the possibly swapped post-GC backing buffer.
- `GarbageClean()` copies live notes into the alternate 0x400-byte buffer and then flips `gc.current_base`; `MusicBox()` makes the offsets drift in non-0x10 steps, so stale offsets can land eight bytes before another packed note header.
- `EditNote()` and `ShowNote()` fall back to `start=0, size=8` whenever the header checksum fails, so a stale pointer that lands eight bytes before a victim header becomes a precise 8-byte read/write primitive onto that header.
- The debugger-free runtime evidence that mattered was timing the first GC around 12.55 seconds and the second GC around 25.30 seconds after process start for the chosen layout, then confirming that stale `show(0)` leaked `00 00 08 00 || checksum` instead of note0's `AAAAAAAA`.

## 3. Exploit Chain

- Stage 1 layout: create three 8-byte notes at offsets `24`, `56`, and `80` before GC1. After compaction they repack to offsets `0`, `16`, and `32`.
- Race `show(0)` across GC1: `GetSlotOffset(0)` snapshots old offset `24`, GC compacts, then `ShowNote()` interprets offset `24` in the new buffer and falls back to reading from `32`, which is note2's header.
- Recover `random_key` from leaked note2 header: `checksum ^ 0x00080000`.
- Stage 2 layout: after GC1, add note3 and note4 so their pre-GC2 offsets are `56` and `80`. Race `edit(3)` across GC2 so the stale offset `56` writes eight bytes onto note4's packed header at offset `64`.
- Forge note4's header as `start=0x7b8, size=8`, which makes normal `show(4)` / `edit(4)` point directly into the slot-metadata array.
- Use note4 to rewrite slot0's metadata:
  - first to `gc.current_base_ptr` and leak the active buffer pointer, which immediately gives the PIE base
  - then to the copy-relocated `stdout` pointer and leak libc
  - finally to `atoi@got-8`, so fallback `edit(0)` becomes a direct 8-byte GOT write
- Overwrite `atoi@got` with `system`, then send `/bin/sh` or `cat /flag` as the next menu choice.
- Decisive insight: treat the no-lock `GetSlotOffset()` result as a stale capability, not as an index helper, and race it across buffer compaction so the checksum-fallback path writes exactly eight bytes onto another note header.

## 4. Dead Ends Worth Remembering

- Trying to reuse the first-stage race with purely line-anchored timings was less stable than the measured absolute windows. The background lyrics were still useful for sanity checks, but the decisive send times were process-age based.
- Treating the note header checksum as a blocker at the start was misleading. You only need the real `random_key` once, and the checksum-fallback path is already enough to leak that one valid header.
- Hunting for a direct GOT target before leaking the active buffer pointer was unnecessary. Leaking `gc.current_base_ptr` first removes PIE uncertainty cleanly and makes the later slot metadata writes deterministic.

## 5. Lessons to Reuse

- Signals that should trigger reuse:
  - a helper returns a compacting-buffer offset or index before taking the lock that guards compaction
  - a later parser or editor has a checksum-failure fallback that still performs a fixed-size read or write
  - a background allocator introduces non-aligned offset drift while compaction repacks live objects into deterministic order
- This mitigation mix strongly prefers metadata corruption over return-address attacks: SHSTK and IBT make direct ROP unattractive, but Partial RELRO still leaves the GOT writable once you can convert the stale-offset race into arbitrary metadata writes.
- Reusable trick: leak one valid object header through the checksum-fallback path, derive the per-process integrity key, then forge a second object whose normal data pointer walks into allocator metadata.
- Should `patterns.md` be updated: no. The exact stale-offset-through-compaction pattern is highly challenge-specific; the reusable lesson is captured here without being common enough yet for the global library.
