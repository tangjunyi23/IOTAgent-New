# CTF Pwn Methodology: ezheap

**Date**: 2026-04-04
**Binary**: pwn
**Architecture**: x86_64
**Mitigations**: NX, PIE, Full RELRO, Canary, SHSTK, IBT
**Vulnerability Class**: heap off-by-one null with largebin metadata abuse
**Primitives**: libc leak, heap leak, fake-chunk unlink, largebin attack, pseudo-tcache arbitrary aligned malloc, stack-targeted syscall-return overwrite, ret2libc
**Reuse Tags**: off-by-one, tcache, rop, ret2libc
**User-Provided ida-no-mcp Pseudocode**: no

## 1. Snapshot

- Menu heap challenge with `add/edit/delete/show`; sizes restricted to roughly `0x450` to `0x550`.
- Local artifacts used: challenge binary plus bundled `libc.so.6` from Ubuntu glibc `2.39-0ubuntu8.7`.
- The initial endpoint `114.66.24.221:31805` timed out, but the later rotated endpoint `114.66.24.221:33595` was exploitable with the same chain.
- Flag recovered: `nctf{c6d45d25-0a89752cefb8e5d-21e2f9bd9}`.

## 2. Ground Truth

- `edit_chunk` performs `read(0, chunk, size)` and then unconditionally writes a trailing NUL at `chunk[nread]`, giving an off-by-one null write.
- For requested sizes congruent to `8 mod 0x10`, such as `0x4f8`, that NUL lands on the next chunk's size LSB; with control of the following `prev_size`, this is a straight House of Einherjar setup.
- Reclaiming a freed `0x528` large chunk through a `0x4f8` allocation leaks both libc and heap from largebin metadata reuse.
- A largebin attack against `mp_.tcache_bins` creates an out-of-bounds "pseudo tcache" entry for the oversized `0x500` class, so later frees of `0x4f8` requests can be poisoned into arbitrary aligned `malloc(0x4f8)` results.
- Runtime testing proved that `__free_hook` is a dead end on this glibc: the symbol exists, but the allocator path no longer uses it.

## 3. Exploit Chain

- Leak libc and heap by freeing `0x4f8/0x528` chunks, reclaiming the large chunk with a bigger request, and showing the overlapped `0x4f8` chunk.
- Build a fake chunk at `heap_hdr - 0x9f0`, patch the next chunk's `prev_size`, and free backward into the fake chunk with House of Einherjar.
- Use the overlap to patch a freed largebin chunk's `bk_nextsize` to `mp_.tcache_bins - 0x20`, then trigger a largebin attack with another `0x548` allocation.
- Free `0x4f8` chunks into the pseudo bin and overwrite the pseudo-bin head at the overlapped chunk's `+0x60` to obtain repeated arbitrary aligned `malloc(0x4f8)` allocations.
- Leak a stack anchor from `program_invocation_short_name` instead of `environ`; on this glibc build, `program_invocation_short_name` reliably contains an `argv[0]` stack pointer while `environ` is zero.
- Scan stack windows below that pointer until the current `show_chunk` frame is identified by the return-address pattern `...2e3`, `...6bb`, `...8a5`, which recovers `main_rbp`.
- Reuse one more poisoned `0x4f8` allocation on a stack window slightly below `main_rbp`, choosing a target that is actually returned by `malloc` and whose `show()` output still exposes the current `show_chunk` saved RIP.
- Final route: overwrite the active single-threaded libc `read()` return address at `main_rbp - 0x48`, not `edit_chunk`'s saved RIP. Because glibc `__read` in the single-thread fast path is effectively `syscall; cmp; ret`, dropping a short `ret; pop rdi; ret; "/bin/sh"; system` chain at that return slot cleanly pivots into `system("/bin/sh")`.
- Decisive insight: once the pseudo tcache gives arbitrary aligned oversized malloc, the shortest stable finish is `program_invocation_short_name` stack leak -> working stack-target probe -> overwrite the current libc `read` return address, because closer edits crash the live `read` frame and `__free_hook` no longer fires.

## 4. Dead Ends Worth Remembering

- `__free_hook` overwrite
  - Failed because glibc 2.39 keeps the symbol for compatibility but the allocator path no longer dispatches through it.
  - Earlier signal: `dlsym(RTLD_DEFAULT, "__free_hook")` returned `NULL`, and local tests showed no code execution even after apparently successful hook writes.

- `environ` leak
  - Failed because the exported `environ` slot in this build was zero, so poisoning around it did not produce a stack pointer.
  - Earlier signal: direct reads around `libc.sym["environ"]` showed zeroed pointers, while nearby `program_invocation_short_name` contained live stack addresses.

- Overwriting `edit_chunk`'s saved RIP directly
  - Failed because practical stack targets that `malloc(0x4f8)` would return were too far below the active frame; the payload hit the live `read()` return slot first and crashed inside `__read`.
  - Earlier signal: the core dump faulted at the `ret` in `__read`, with the fault address taken from filler bytes, proving the current syscall frame must be targeted or preserved.

## 5. Lessons to Reuse

- If an oversized pseudo-tcache primitive is limited to aligned addresses, probe libc global variables that already store stack pointers before spending time on `environ`; `program_invocation_short_name` is a strong candidate on modern glibc.
- When a stack-targeted heap write is delivered through a live `read()` call, always map the current syscall-return slot first. A shorter overwrite on the syscall frame can be cleaner than trying to survive back to the caller frame.
- Largebin-to-`mp_.tcache_bins` corruption can create a usable pseudo tcache even for sizes above the normal tcache maximum; once that is confirmed, treat it as repeated arbitrary aligned malloc, not as a one-off allocation.
- Should `patterns.md` be updated: no. The technique is useful, but the strongest lesson here is a compound route specific to glibc 2.39 plus this menu layout, not a broad new canonical pattern.
