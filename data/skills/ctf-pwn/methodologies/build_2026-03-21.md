# CTF Pwn Methodology: Build

**Date**: 2026-03-21
**Binary**: `pwn`
**Architecture**: `x86_64`
**Mitigations**: `NX`, `Partial RELRO`, `No PIE`, `No Canary`, `No Fortify`, `No seccomp observed`
**Vulnerability Class**: stack overflow / controlled stack write
**Primitives**: stack leak, arbitrary stack write target via OOB index, self-amplified read, ret2libc
**Reuse Tags**: stack-overflow, ret2libc, rop
**User-Provided ida-no-mcp Pseudocode**: no

## 1. Snapshot

- Goal: exploit the service at `challenge.imxbt.cn:31460` and recover the flag.
- Artifacts used: `Build.zip` containing `pwn` and `libc.so.6`, plus a fresh headless IDA export generated from the local binary.
- Remote runtime matched the local binary prompts, but the service used a minimal shell environment: `/dev/null` redirection failed and `head` was unavailable.

## 2. Ground Truth

- `pwn` is a non-PIE `ET_EXEC` amd64 binary with `NX` and `Partial RELRO`; there is no stack canary.
- `sub_401205` prints `Gift for you:%p` with the address of a local `char s[16]`, which leaks a stable stack pointer.
- `main` allocates `v5[17]` at `[rbp-0xb0]` and then loops `for (i = 0; i <= 17; ++i) scanf("%llu", &v5[i])`. Index `17` lands on `[rbp-0x28]`, which is the `buf` pointer later passed to `read`.
- The final sink is `read(0, buf, ++nbytes)`. After setting `buf = leak + 0x18`, the first `read` writes onto its own saved return address. Offsets from the leaked pointer were:
  - `read_ret = leak + 0x18`
  - `buf = leak + 0xa8`
  - `saved_rbx = leak + 0xc8`
  - `saved_rbp = leak + 0xd0`
  - `saved_rip = leak + 0xd8`
- The binary has a useful gadget at `0x4011fe`: `xchg rdi, rbx; ret`. Combined with control over `saved_rbx` and `saved_rip`, this gives a one-argument ret2libc call primitive.

## 3. Exploit Chain

- `Build 0` must equal the deterministic value `rand() * rand() = 0xaeb1c2aa` on the first entry, or the core-energy check aborts. Because the process never calls `srand`, the second `main` re-entry always uses `0x4500ff2b`.
- Stage 1:
  - Use the stack leak to compute `read_ret`.
  - Set `Build 17 = read_ret`, so the final `read` writes over its own return address.
  - Repeatedly send short chunks that overwrite the current `read` return address with `0x4013c0`, which loops back into `++nbytes; read(...)`.
  - Once the write passes offset `0x90`, also restore `[rbp-0x28]` to `read_ret`, so later reads keep targeting the same stack slot.
  - On the final pumped read, overwrite the epilogue slots so `main` returns into `xchg rdi, rbx; ret`, then into `puts@plt(puts@got)`, then through a single `ret` back into `main`.
  - Parse the raw leaked GOT bytes to recover `libc_base`.
- Stage 2:
  - Reuse the new `Gift for you:%p` leak from the re-entered `main`.
  - Important: `nbytes` lives in `.bss` and is not reset by re-entering `main`. After stage 1 pumps it to `0xe0`, the very next `read` already accepts `0xe1` bytes, so stage 2 is a single-shot full overwrite.
  - Set `saved_rbx = libc_base + "/bin/sh"` and `saved_rip = xchg rdi, rbx; ret`, followed by `system`.
  - Send a shell command that prints `READY` and then `cat /flag`.
- Decisive insight: the tiny final `read` is still enough because the OOB write can point it at its own return address, and the persistent global `nbytes` turns the first-stage pump into a full second-stage write on the same connection.

## 4. Dead Ends Worth Remembering

- Bulk-sending the entire stage-1 pump worked locally over pipes but failed remotely over TCP.
- The reason was stream short-read behavior: the service could consume fewer bytes than the intended staged length, desynchronizing the self-amplifying loop.
- The earlier signal was that the primitive relies on many consecutive `read` calls on a socket, not a local pipe, so paced per-read sends were safer than one giant send.

## 5. Lessons to Reuse

- Signals to watch for:
  - a stack leak near a later `read`
  - an off-by-one or OOB index that can rewrite the future destination pointer of that `read`
  - a writable return address for the currently executing `read`
  - a global byte-count variable that survives function re-entry
- Mitigation mix:
  - `No PIE` made the small gadget and PLT addresses stable.
  - `NX` pushed the route toward ret2libc, but the lack of a canary made the stack-frame overwrite straightforward.
- Reusable trick:
  - self-amplify a tiny read by writing onto the active call’s return slot, then restore any clobbered destination pointer mid-stream.
  - if the service sits behind a socket, pace the staged sends instead of assuming one large send will map 1:1 onto future `read` lengths.
- Should `patterns.md` be updated: yes. Add the warning that self-amplifying read chains over TCP can desynchronize on short reads and may need paced chunked sends.
