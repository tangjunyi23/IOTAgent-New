# CTF Pwn Methodology: deepvoid

**Date**: 2026-05-14
**Binary**: `deepvoid`
**Architecture**: `x86_64`
**Mitigations**: `NX`, `Partial RELRO`, `No PIE`, `Canary`, `FORTIFY`
**Vulnerability Class**: heap overflow with unsafe unlink
**Primitives**: heap chunk header forgery, unsafe unlink table pivot, GOT leak via `free@got -> puts@plt`, parser hijack via `strtol@got -> system`
**Reuse Tags**: heap-overflow, ret2libc
**User-Provided ida-no-mcp Pseudocode**: no

## 1. Snapshot

- The service at `39.96.193.120:55555` exposes a three-action heap menu: create, modify, remove.
- Local artifacts used: `deepvoid`, bundled `libc.so.6`, and the matching `glibc-all-in-one` loader bundle for `2.23-0ubuntu11.3_amd64`.
- The remote `system()` path is wrapped: it only allows `"sh"` or `"/bin/sh"`, so direct `system("cat /flag")` is rejected.

## 2. Ground Truth

- `file`, `checksec`, and `readelf` show a 64-bit non-PIE binary with NX, partial RELRO, stack canary, and writable GOT.
- `create_item()` stores a raw heap pointer in the global `chunks[10]` array at `0x6020c0`, with no size metadata tracked in parallel.
- `modify_content()` validates the slot index but then always executes `read(0, chunks[idx], 0x200)`, regardless of the allocation size. Any chunk smaller than `0x200` is therefore overflowable.
- `remove_entry()` frees `chunks[idx]`, then clears the slot, so a forged previous chunk in chunk 0 can target chunk 1 and trigger old-school glibc `unlink` on Ubuntu glibc 2.23.
- The decisive runtime detail was not the unlink itself, but the command parser: `get_numeric_input()` does `read(0, buf, 0xf)` and never appends `'\0'`. After hijacking `strtol@got` to `system`, a normal `"sh\n"` is not reliable because stack garbage trails the string. A raw `b"sh\\x00"` is required.

## 3. Exploit Chain

- Allocate three `0x80` chunks.
- Overflow chunk 0 with a fake free chunk header: `fd = chunks-0x18`, `bk = chunks-0x10`, then corrupt chunk 1's `prev_size` and clear its `prev_inuse` bit by writing `size = 0x90`.
- Free chunk 1 to trigger backward consolidation and `unlink`, which rewrites `chunks[0]` into a pointer to `chunks-0x18`.
- Use `modify(0, ...)` once more to rewrite the visible slot table so that:
  - slot 0 points to `free@got`
  - slot 1 points to `read@got`
  - slot 2 points to `strtol@got`
- Overwrite `free@got` with `puts@plt`, then delete slot 1. `remove_entry()` becomes `puts(read@got)` and leaks `read` from libc.
- Compute the libc base from `read`, then overwrite `strtol@got` with `system`.
- Trigger the next menu parse with raw bytes `b"sh\\x00"`, wait briefly for the shell to spawn, then send `cat /flag 2>/dev/null; cat /home/*/flag* 2>/dev/null; exit`.
- Decisive insight: once the GOT pivot exists, hijacking the numeric parser (`strtol@got -> system`) is cleaner than spending another slot on a `/bin/sh` pointer, but only if the trigger is a NUL-terminated raw send rather than a newline-terminated menu string.

## 4. Dead Ends Worth Remembering

- Route attempted: overwrite `strtol@got` with `system` and immediately send `cat /flag`.
- Why it failed: the remote wrapper only allows `"sh"` or `"/bin/sh"` as the `system()` argument.
- Earlier warning sign: the official service banner from the wrapped `system` made it obvious the challenge author intended shell-spawn first, not direct one-shot commands.

- Route attempted: overwrite `strtol@got` with `system` and trigger it with `sendline(b"sh")`.
- Why it failed: `get_numeric_input()` leaves the stack buffer unterminated, so `system()` sees `sh` plus trailing stack junk and the wrapper rejects it.
- Earlier warning sign: any `read()`-backed parser turned into a C-string consumer must be checked for explicit NUL termination first.

## 5. Lessons to Reuse

- On glibc 2.23 partial-RELRO binaries with a global pointer table, classic unsafe unlink still matters when a menu write ignores allocation size.
- After converting a numeric parser into `system`, the final trigger path may be more constrained than a heap-backed `"/bin/sh"` string, but it can save a full extra pointer repoint if the parser buffer can be cleanly NUL-terminated.
- Remote wrappers around `system()` can force the exploit back toward an interactive shell even after a seemingly more elegant one-shot-command hijack.
- Should `patterns.md` be updated: no. The `raw "sh\\x00"` trick is useful, but it is still too tied to this exact `read()`-without-NUL parser conversion pattern to justify a global rule yet.
