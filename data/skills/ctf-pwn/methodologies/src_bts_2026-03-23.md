## 2. Ground Truth

- The service is pure Python, but `Buffer.write()` / `Buffer.read()` dereference raw addresses through `ctypes`:
  - `self.ptr` is initialized once from `PyByteArray_AsString(self.data)`.
  - `resize()` never refreshes `self.ptr`.
  - The shrink path `self.data = self.data[:new_size]` always allocates a new `bytearray`, leaving `self.ptr` stale.
- Exploit proof:
  - `Reveal` leaks the original backing-buffer address.
  - `Grow(1)` after an initial `Prepare(16)` creates a guaranteed stale pointer.
  - A second `Grow(600000)` only increases the bounds check (`self.size`) on the new buffer, while `read` / `write` still dereference the old pointer, giving large relative byte-wise access from the leaked base.
- The decisive debugger-style fact from runtime probing was that attacking CPython dict internals was unnecessary. The easier target was `main.__code__.co_names`, whose tuple stores direct `PyObject *` entries for global names used by `LOAD_GLOBAL`.
- On the unmodified socket service, the first `Prepare(16)` gave stable offsets from the leaked stale pointer:
  - `int` name-slot in `main.__code__.co_names`: `+250096`
  - existing `'eval'` string object: `+481536`

## 3. Exploit Chain

- Trigger:
  - `Prepare(16)` to allocate a small `bytearray` in the CPython small-object arena.
  - `Reveal` leaks the original buffer address.
  - `Grow(1)` forces `self.data = self.data[:1]`, making `self.ptr` stale.
  - `Grow(600000)` enlarges the allowed offset range without fixing the stale pointer.
- Overwrite:
  - Read the qword at offset `+250096` and confirm it is the static `'int'` string object pointer `0x998d80`.
  - Overwrite that qword with `ptr + 481536`, the address of the already-existing `'eval'` string object.
  - This mutates `main.__code__.co_names` so every later `LOAD_GLOBAL int` in `main()` resolves the builtin name `eval` instead.
- Triggered call site:
  - Re-enter menu option `1` (`Prepare`) and send:
    - `__import__("os").system("cat flag.txt") or 0`
  - The source still executes `size = int(line)`, but the name lookup now resolves to `eval(line)`, so the expression runs and prints the flag.
  - `or 0` keeps the branch alive by returning a valid integer size.
- Decisive insight: once a CPython service gives a stale raw pointer, repoint a code object’s `co_names` entry from `'int'` to an existing `'eval'` string object instead of fighting dict key tables or builtin function objects.

## 4. Dead Ends Worth Remembering

- Dead end: targeting `builtins` / module dict internals first.
- Why it failed: the dict key table (`ma_keys`) lived on the lower malloc heap, while fresh attacker-controlled heap buffers were allocated above it, so the relative stale-pointer primitive could not reach it reliably.
- Earlier signal: the service already had a stable Python-level call site (`int(...)`) in `main()`, so a code-object metadata overwrite was a shorter path than dict surgery.

- Dead end: measuring offsets from helper scripts that merely `import server`.
- Why it failed: the socket-driven `python3.11 server.py` runtime performs extra `input()` / stdio work before the first buffer allocation, shifting CPython small-object placement.
- Earlier signal: the exploit depends on object adjacency inside the real interpreter event path, so offsets must be measured in the same menu-driven execution mode.

## 5. Lessons to Reuse

- Signals to watch for:
  - a Python service exposing raw addresses through `ctypes`
  - stale pointers after `bytearray` slicing or reallocation
  - a repeated builtin call like `int(...)` / `open(...)` / `input(...)` in a hot Python function
  - a leaked small-object buffer that lands near code-object tuples or interned strings
- Mitigation mix:
  - Native ELF mitigations were mostly irrelevant; the real constraint was CPython allocator and object-layout behavior under ASLR.
  - Stable low addresses for some interned or builtin name objects made tuple-slot confirmation straightforward once the stale base was leaked.
- Reusable trick:
  - in CPython object-corruption challenges, prefer retargeting `function.__code__.co_names` to an already-existing builtin name object when a later call site gives attacker-controlled arguments.
  - this can be much shorter and more reliable than rebuilding dict entries, patching builtin function objects, or chasing lower-heap key tables.
- Should `patterns.md` be updated: yes. Add a generalized note under `uaf` / interpreter-object corruption that code-object name tuples can be easier targets than dict internals when the goal is to repurpose an existing builtin call.
