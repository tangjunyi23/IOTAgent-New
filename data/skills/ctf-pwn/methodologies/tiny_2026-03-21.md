# CTF Pwn Methodology: tiny

**Date**: 2026-03-21
**Binary**: `tiny`
**Architecture**: `x86_64`
**Mitigations**: `NX`, `Full RELRO`, `PIE`, `No Canary`, `No seccomp observed`
**Vulnerability Class**: `stack overflow plus arbitrary file read via path traversal`
**Primitives**: `arbitrary file read`, `stack overwrite of saved registers and saved RIP`, `maps leak`, `exact stack buffer address leak through /proc/self/mem`, `ret2libc`
**Reuse Tags**: `stack-overflow, pie-leak, ret2libc, rop`
**User-Provided ida-no-mcp Pseudocode**: no

## 1. Snapshot

- Goal: solve the local `tiny.zip` bundle and recover the shortest reliable exploit path, then replay it against `challenge.imxbt.cn:32174`.
- Artifacts used: `tiny`, bundled `libc.so.6`, bundled `ld-linux-x86-64.so.2`, and a fresh headless IDA export from the local binary.
- The remote host used the same binary under `/opt/challenge/tiny`. Its front-end required a correct `Host` header; using `Host: x` triggered an unrelated Apache error page.

## 2. Ground Truth

- `tiny` is an amd64 PIE web server with `NX`, `Full RELRO`, and no stack canary. It forks one child per connection and keeps the same ASLR layout across children.
- `parse_request` copies the URL path into a stack buffer and then calls `url_decode` into `process`'s `file` buffer without a bound that matches the destination.
- Runtime readback through `../../../../proc/self/mem` proved the decisive stack layout in `process`:
  - `file + 0x200`: range start
  - `file + 0x208`: range end
  - `file + 0x218`: saved `rbx`
  - `file + 0x220`: saved `rbp`
  - `file + 0x228`: saved `r12`
  - `file + 0x230`: saved `r13`
  - `file + 0x238`: saved `r14`
  - `file + 0x240`: saved `r15`
  - `file + 0x248`: saved `RIP`
- The same request parser also strips only the leading `/` and never sanitizes `..`, so `GET /../../../../etc/hostname` and `GET /../../../../proc/self/maps` both succeed.
- `Range` headers, or direct overwrites of `file+0x200/+0x208`, let the service read arbitrary offsets from procfs pseudo-files, including `/proc/self/maps` and `/proc/self/mem`.
- Remote `/proc/self/status` proved `x86_Thread_features` was empty, so CET was not actually enabled at runtime. The earlier crashes came from request-serialization mistakes, not shadow stack enforcement.

## 3. Exploit Chain

- Stage 1: use path traversal to read `../../../../proc/self/maps` and recover the PIE base, libc base, and top of the stack mapping.
- Stage 2: open `../../../../proc/self/mem` in a separate child, overwrite `file+0x200/+0x208` with a stack range, and search the leaked memory for the known path prefix to recover the exact `file` buffer address. Because the process is fork-per-connection, that stack address stays stable across children.
- Stage 3: overflow `file` again, but this time store the command string itself at the start of the buffer and place a ret2libc chain at `file+0x218`:
  - `dup2(4, 1)`
  - `dup2(4, 2)`
  - `system(file_buf)`
  - `exit(0)`
- Remote command: `exec /flag`
- Verified remote flag: `cube{1_h0p3_y0u_br0ught_c4rr0ts_6f0bffad}`
- Decisive insight: the file-read bug is enough to leak the exact stack buffer address from one forked child, which turns the second child into a clean `system(file_buf)` ret2libc even though the command string itself contains bad HTTP bytes.

## 4. Dead Ends Worth Remembering

- Route attempted: `dup2(4, 0/1/2); system("/bin/sh")` with the shell command bytes queued immediately after the HTTP request.
- Why it failed: `rio_readlineb` pre-read attacker data into its 0x400 internal buffer while parsing headers, so the future shell never saw the queued bytes on the socket.
- Earlier signal that should have warned about the failure: the vulnerable path sits behind a buffered line reader, so “send exploit and shell commands in one packet” was always at risk of being eaten before control returned.

## 5. Lessons to Reuse

- Signals to watch for:
  - web-style request parsers inside pwn bundles
  - `..` path segments reaching `open()` unchanged
  - `Range` handling on procfs targets like `/proc/self/maps` or `/proc/self/mem`
  - a fork-per-connection model that preserves ASLR and stack addresses across children
- Mitigation mix:
  - `No Canary` still made the overflow easy to prove.
  - `PIE` stopped mattering once `/proc/self/maps` was readable.
  - `Full RELRO` removed GOT writes, but the direct ret2libc route was still short once the exact stack buffer address was known.
- Reusable trick:
  - when procfs is readable, `/proc/self/mem` plus attacker-controlled range fields is a strong way to prove exact stack offsets and recover an exact stack-buffer pointer without a debugger.
  - when the post-exploitation target is `system`, embedding the command string inside the same overflowed stack buffer avoids line-reader buffering issues on the socket.
- Should `patterns.md` be updated: yes. Add the generalized lesson about buffered request readers swallowing queued shell input and about using `/proc/self/mem` to recover a reusable stack-buffer address across forked children.
